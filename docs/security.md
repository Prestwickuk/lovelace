# LOVELACE Booking System — Security Controls

## 1. Authentication, Sessions & Password Policy
- **Hashing:** Argon2id (`m=65536`, `t=3`, `p=1`) in `internal/auth`.
- **Sessions:** 256-bit CSPRNG session tokens stored hashed (SHA-256) in `admin_sessions`, delivered via `tirbach_session` cookie (`HttpOnly`, `SameSite=Lax`, `Secure` required in `production`). Sliding idle timeout + absolute session TTL enforced server-side.
- **Forced Password Rotation:** Accounts flagged `must_rotate_password = TRUE` are gated to `/api/v1/auth/me`, `/api/v1/auth/logout`, `/api/v1/auth/change-password`, and `/account?rotate=1` until password rotation succeeds; rotation revokes all prior sessions atomically.
- **Rate Limiting:** Per-IP + per-account sliding-window brute-force throttling returning `429` (`TIRBACH_TRUST_PROXY=true` required behind a reverse proxy).

## 2. CSRF, Headers & CSP Hygiene
- All state-changing API and form handlers validate a per-session `X-CSRF-Token` / hidden `csrf_token` with constant-time comparison.
- Strict Content Security Policy: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; object-src 'none'; frame-ancestors 'none'` — **zero inline `<script>` or `style="..."` attributes** exist in templates (`internal/webui/templates/*.html`).
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.
- Browser and API errors never leak stack traces or SQL internals; Web UI RBAC/route errors render LOVELACE-branded `error.html`.

## 3. Immutable Audit Logging (`0003_phase1_5.sql`)
- `trg_audit_logs_immutable` (`BEFORE UPDATE OR DELETE FOR EACH ROW`) blocks row edits and deletions unconditionally.
- `trg_audit_logs_no_truncate` (`BEFORE TRUNCATE FOR EACH STATEMENT`) blocks `TRUNCATE TABLE audit_logs` for every role including table owners/superusers unless **both**:
  1. `current_database() ~ '(_test|-test)$'` AND
  2. Transaction-local GUC `tirbach.test_reset_token = 'allow_test_reset'` is set (`SET LOCAL`).

## 4. Isolated Test Database Verification
`verifySafeTestDatabase` in `internal/app/integration_test.go` fails closed unless:
- URL & `SELECT current_database()` both end with `_test` or `-test`, agree, and do not contain `prod`.
- Connection host is loopback (`127.0.0.1`, `localhost`, `::1`, or local socket).
- Connected PostgreSQL role is **non-superuser** (`rolsuper = false`), non-`postgres`, and non-`tir_bach`.
Provisioned via `scripts/setup-test-db.sh` (`tir_bach_test_runner`).

## 5. Production Fail-Closed Configuration & Least-Privilege DB Roles
When `TIRBACH_ENV=production`, `internal/config/config.go` refuses startup if `TIRBACH_COOKIE_SECURE=false`, `TIRBACH_AUTO_SEED=true`, `TIRBACH_ENCRYPTION_KEY` is missing/weak/dev-default, or `DATABASE_URL` uses known dev credentials. `cmd/server` also queries `pg_roles` via `InspectRolePrivileges` and refuses to boot in `production` if connected as a `SUPERUSER`, `CREATEDB`, or `CREATEROLE` role. PostgreSQL bootstrap credentials stay isolated inside `postgres`/`db-bootstrap`; schema DDL runs exclusively under `lovelace_migrator`; runtime traffic uses strictly DML-only `lovelace_app`.

## 6. Public vs. Administrative Origin & Boundary Isolation (Phases 2–5)
- **Separate Origins & Deployments:** The Administrative console and future Public booking frontend run as distinct frontend builds on separate origins (separate domain/subdomain and independent static/template delivery).
- **Cookie, Session & CSRF Isolation:** Administrative sessions (`tirbach_session` cookie) and CSRF tokens must be scoped strictly to the administrative origin (`Domain` omitted / host-only, `HttpOnly`, `Secure` in production, `SameSite=Lax`/`Strict`), completely disjoint from any future customer/guest portal session mechanism on public origins.
- **CORS & CSP Separation:** The administrative backend and web UI enforce deny-all cross-origin access (`Access-Control-Allow-Origin` omitted on admin APIs) and strict CSP; any future public API endpoints expose an explicit allowlist of configured property origins (`properties` domain mapping) rather than wildcard credentials.
- **No Frontend Security Boundary:** Public frontends receive zero administrative routes/code/credentials (`channel_connections`, `admin_users`, `audit_logs`), and administrative handlers enforce server-side session + RBAC verification independently of caller origin.

## 7. Phase 2.1 Public Checkout, Token & Proxy Hardening
- **Server-Derived Checkout Redirects:** `POST /api/public/v1/checkout` and BFF `/api/public/booking/checkout` reject client-supplied `success_url` / `cancel_url`. Return URLs are constructed exclusively server-side from configured HTTPS public origins / verified property domains and validated by `payments.ValidateCheckoutReturnURL` (blocking external redirects, protocol-relative URLs, non-HTTPS production URLs, and subdomain spoofs). Sandbox checkout routes derive relative same-origin destinations only and are disabled in production.
- **One Active Payment Attempt Per Hold:** `payment_attempts` enforces a PostgreSQL partial unique index (`uq_payment_attempts_one_active_per_hold`) paired with hold-row `FOR UPDATE` locking. Concurrent checkout requests with distinct idempotency keys cannot spawn competing Stripe Checkout Sessions for a single hold; identical idempotent replays reuse the existing session, and bounded retries (max 3) are permitted only after definitive failure.
- **Confirmation Bearer Token Hygiene:** Confirmation lookup requires both reference and high-entropy 256-bit token (`SHA-256` hashed at rest, revocable via `/rotate-token`, `expires_at` scoped tightly on holds and extended post-stay upon confirmation). Query-string tokens (`?token=...`) are rejected by the backend (`400 query_token_forbidden`) and stripped client-side; lookups use `POST` or `Authorization: Bearer` with `Cache-Control: no-store, private`, `Referrer-Policy: no-referrer`, and `X-Robots-Tag: noindex, nofollow`.
- **Trusted Proxy, Server-Only BFF & Process-Local Rate Limiting:** Both Next.js BFF and Go backend enforce per-client and global rate limits using process-local counters (valid for the single-Go + single-Next.js launch topology; migrate to a shared store such as Redis before scaling horizontally). `X-Forwarded-For` is walked right-to-left strictly against configured trusted proxy CIDRs; direct Go public API calls in production require server-to-server `X-Lovelace-Public-Key` (`TIRBACH_PUBLIC_API_SECRET`), and `apps/public-web/src/lib/lovelace-api.ts` enforces `import "server-only"` so the BFF secret cannot enter browser bundles.
- **Live Stripe Mode, Webhook `livemode` & Mandatory Email Readiness:** `LogSender` is never wired as a genuine mail transport; unconfigured SMTP retains outbox items in `PENDING`. In `production`, test-mode Stripe keys (`sk_test_`/`rk_test_`) fail closed (requiring `sk_live_`/`rk_live_` paired with live `whsec_` whenever any property enables `stripe_enabled=true`), incoming webhooks verify signed `livemode` against the configured key mode (recording mismatches to `audit_logs` as `payment.webhook_livemode_mismatch` and `payment_webhook_events.status='REJECTED'` idempotently), and properties accepting live public bookings (`stripe_enabled=true`) always require a genuine SMTP provider (admin-only or payments-disabled operation without SMTP is permitted only when `TIRBACH_REQUIRE_EMAIL=false`).

## 8. Phase 3 Milestone 3 + 3.3.1 Guest CRM, Outbound Email & PII Controls
- **Public API, Template & Internal Note Isolation:** Guest CRM profiles, duplicate reviews, `guest_notes`, enquiries, and communications history reside strictly inside `/api/v1/properties/{propertyID}/*` and LOVELACE admin Web UI (`/guests`, `/enquiries`, `/communications/settings`). `/api/public/v1/*` and `apps/public-web/` receive zero CRM endpoints or records. Internal `guest_notes` and `INTERNAL` enquiry messages (`direction = 'INTERNAL'` ⇔ `is_internal = TRUE`) are never exposed to message template variables (`BuildReservationTemplateVars`) or outbound emails.
- **SMTP Header Injection, Guest-Reservation Integrity & Recipient Guardrails:** Both `SMTPSender.Send` and `LogSender.Send` validate single recipients (`mailer.ValidateMessage`) and reject `\r` / `\n` / control bytes in subjects and headers (`SanitizeEmailHeaderValue`). Template rendering uses Go `html/template` auto-escaping on HTML bodies paired with plain-text fallback and a strict placeholder allowlist (`AllowedTemplatePlaceholders`). Sending emails, previewing templates (failing closed on unknown IDs), logging communications, creating/updating enquiries, and adding notes all enforce canonical guest-to-reservation ownership in both the service layer and PostgreSQL triggers (`enforce_guest_reservation_link`).
- **Delivery Webhook Signature & Production Enforcement:** Inbound provider events (`POST /api/v1/webhooks/email-events`) require valid HMAC-SHA256 `X-Email-Signature` when `TIRBACH_EMAIL_WEBHOOK_SECRET` is configured (and webhook secrets/verification follow fail-closed production hygiene).
- **CRM RBAC, Lifecycle & Consent Immutability:** PostgreSQL composite constraints and triggers guarantee cross-property isolation, restrict generic guest create/update endpoints to operational statuses (`ACTIVE`, `VIP`, `DO_NOT_CONTACT`) so `MERGED`/`ANONYMIZED` require dedicated workflows, and enforce append-only immutability with server-generated `occurred_at` on `guest_consent_records` (defaulting guests without consent history to `NOT_SUBSCRIBED`). `housekeeping_staff` and `maintenance_staff` have zero `guests:*` / `comms:*` permissions; `viewer` cannot read `guest_notes`, `guest_enquiries`, `guest_communications`, `guest_consent_records`, or `guest_merge_events` snapshots; only `owner_admin` and `manager` hold `guests:merge`, `guests:export`, `guests:anonymize`, and `comms:templates`.
- **Operational CRM Export vs. Formal GDPR SAR Review:** `ExportGuestData` exports unbounded customer records (all enquiries, enquiry messages, communications, notes, preferences, reservations, confirmed guest-linked `booking_holds` without session secret hashes, recursive multi-hop `merge_history`, `duplicate_dismissals` without staff attribution, and `consent_history`) with staff identity attribution minimized and an explicit `export_scope_notice` directing operators to apply third-party/exemption review before issuing a formal UK GDPR Art. 15 Subject Access Request package. `property_retention_policies` remain advisory-only (`auto_anonymize_enabled=true` rejected until a reviewed retention worker exists).
- **Phase 3.3.2 Final Acceptance — Audit Snapshot Allowlist Security, Worker Liveness Fencing, Consent Overlays & Reconciliation Governance (`0015`–`0018`):** New CRM, reservation, hold, and all supported LOVELACE mutations record strictly allowlisted structural snapshots in `audit_logs` (`audit_sanitizer.go`) with pseudonymous `guest@public.lovelace` actor attribution for public booking actions; historical raw-PII entries can be masked via the append-only `audit_log_redactions` overlay (`POST /api/v1/properties/{propertyID}/audit-logs/{auditLogID}/redact`, requiring both `guests:anonymize` and `audit:read`) without altering immutable `audit_logs` triggers. Outbound queue dispatch (`ClaimDueOutboxEmails` -> `BeginOutboxDispatchLease` -> renewable `RenewOutboxDispatchHeartbeat` + monotonic `dispatch_fence_epoch`, evaluated under PostgreSQL `clock_timestamp()`) runs context-bounded `SMTPSender.Send(ctx, msg)` outside any DB transaction (`DefaultDispatchConfig()`: `60s` lease, `20s` heartbeat, `30s` transport timeout), cancelling sockets immediately on timeout, fencing, expired lease, or heartbeat DB error and distinguishing pre-DATA aborts (`TERMINATED_BEFORE_SEND`) from post-DATA timeouts (`UNCERTAIN_TIMEOUT` -> `DISPATCH_UNKNOWN`). Live heartbeating workers are never swept solely on elapsed runtime; expired leases cannot be renewed or settled even prior to sweeping. Uncertain dispatches require `comms:reconcile` (`owner_admin`/`manager` only; hidden from `staff` UI), an active `must_rotate_password = FALSE` user verified in PostgreSQL within property scope, zero live dispatch leases (`409`), and non-PII structured evidence (`MTA_REJECTED`/`PROVIDER_WEBHOOK_FAILED`/`PROVIDER_NOT_SUBMITTED` required for `CONFIRMED_FAILED`/`CANCEL`) persisted in `email_outbox.reconciled_*` and `audit_logs`. `guest_consent_records` stays append-only (`UPDATE(guest_id)` allowed only for merges), while `guest_consent_redactions` and `audit_log_redactions` enforce controlled `reason_category`, canonical replacement placeholders, `validate_non_pii_reason(...)` (email, international/UK phone, control-char checks), strict per-`resource_type` JSONB allowlist validation (`validate_audit_redaction_snapshot` + `audit_resource_key_rule` in `0018`, synchronized 1:1 with `audit_sanitizer.go` and looking up `audit_logs.resource_type` authoritatively), and `BEFORE INSERT` table triggers; both `SECURITY DEFINER` redaction functions pin `search_path = pg_catalog, public` and enforce active `owner_admin`/`manager`, `must_rotate_password = FALSE`, and property scope, with `lovelace_app` holding zero direct table privileges on overlay tables.
